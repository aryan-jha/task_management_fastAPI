1. ORM Fundamentals 10 / 10

This is the foundation. Everything later — Session, Engine, models, metadata — sits on the idea that Python objects and database rows are two views of the same data.

1. What does ORM mean?

ORM stands for Object-Relational Mapping.

It is a technique that allows us to work with relational database data using programming-language objects instead of writing SQL for every database operation.

The basic mapping is:

Classmaps to a table
Objectmaps to a row
Attributemaps to a column
Python                         Database

Class        ───────────────→  Table
Object       ───────────────→  Row
Attribute    ───────────────→  Column

2. Example

class User:
    id
    name
    email

Conceptually this represents:

users
+----+-------+-------------------+
| id | name  | email             |
+----+-------+-------------------+
| 1  | Aryan | aryan@example.com |
+----+-------+-------------------+

A Python object could be:

user = User()

user.id = 1
user.name = "Aryan"
user.email = "aryan@example.com"

The ORM maps that object to the database row.

3. Why do ORMs exist?

Without an ORM, application code may repeatedly contain raw SQL:

SELECT id, name, email
FROM users
WHERE id = 1;

Then application code has to manually convert the returned database row into an appropriate Python representation.

An ORM handles much of this mapping for us.

4. SQLAlchemy ORM

With SQLAlchemy, we can define:

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    email: Mapped[str]

SQLAlchemy understands that User is an ORM model corresponding to the users database table.

5. Why use an ORM?

  • Maps database rows to Python objects.
  • Reduces repetitive SQL boilerplate.
  • Provides object-oriented access to database data.
  • Provides relationships between models.
  • Provides transaction/session management.
  • Allows complex queries while retaining Python-level abstractions.
  • Works with database-specific SQL dialects.

6. Disadvantages of ORMs

  • Can hide SQL and make database behavior harder to understand.
  • Incorrect ORM usage can produce inefficient queries.
  • Complex queries may require understanding SQL anyway.
  • Abstraction can make debugging harder if the developer does not understand what SQL is generated.
  • There can be performance pitfalls such as the N+1 query problem.

7. ORM vs Raw SQL

Raw SQL:

SELECT *
FROM users
WHERE email = 'aryan@example.com';

SQLAlchemy ORM:

stmt = select(User).where(
    User.email == "aryan@example.com"
)

user = db.scalar(stmt)
Same destination. The ORM version still eventually results in SQL being executed against the database.

7. Session

The Session is the ORM's main workspace for managing ORM objects, database operations, and transactions.

Not the database. The Session is a workspace. It is not PostgreSQL itself.

8. Engine

The Engine is SQLAlchemy's database connectivity infrastructure.

It coordinates connections and communication with the database driver.

A connection pool maintains reusable database connections.

Instead of establishing a brand-new database connection for every operation, the application can reuse connections managed by the pool.

The driver is the Python library that knows how to communicate with PostgreSQL.

For example, a PostgreSQL application can use a driver such as psycopg.

This is the actual relational database server storing tables, rows, indexes, constraints, and data.

3. SQLAlchemy 2.x Basics 10 / 10

SQLAlchemy 2.x puts type annotations on the model and uses select() instead of the old query API. Learn the pieces by name so later topics have somewhere to attach.

1. Modern Declarative Base

from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass

Base is the base class from which ORM models inherit.

2. Modern model syntax

from sqlalchemy.orm import Mapped, mapped_column

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    email: Mapped[str]

3. What the pieces mean

User
 ↓
ORM model

__tablename__
 ↓
database table name

Mapped[int]
 ↓
Python-side type and ORM mapping information

mapped_column(...)
 ↓
database column configuration

4. Why SQLAlchemy 2.x typing?

SQLAlchemy 2.x provides a typed declarative style that integrates Python type annotations directly into ORM model definitions.

For example:

id: Mapped[int]
name: Mapped[str]
email: Mapped[str | None]

This makes the model easier to understand and works well with modern Python type checking.

5. select()

from sqlalchemy import select

stmt = select(User)

stmt is simply a common variable name meaning statement.

It does not have special meaning in SQLAlchemy. You could call it:

statement = select(User)
query = select(User)
Construct, don't run. select(User) constructs a SQLAlchemy statement. It does not by itself execute the query.

6. Executing a statement

result = session.execute(stmt)

execute() sends the statement through the Session for execution and returns a SQLAlchemy result object.

7. scalars()

result = session.scalars(stmt)

scalars() gives scalar values from the result. When the statement selects ORM entities such as User, those scalar values are User objects.

For example:

users = session.scalars(
    select(User)
).all()

produces something conceptually like:

[
    <User id=1 name='Aryan'>,
    <User id=2 name='John'>
]

8. scalar()

user = session.scalar(
    select(User).where(User.id == 10)
)

This is useful when you expect one scalar result.

9. execute() vs scalars()

Conceptually:

session.execute(stmt)
    ↓
Result rows / row-oriented result

session.scalars(stmt)
    ↓
scalar values from the rows

session.scalar(stmt)
    ↓
one scalar value
CallYou get back
session.execute(stmt)Result rows / a row-oriented result
session.scalars(stmt)Scalar values from those rows
session.scalar(stmt)One scalar value

10. Example

stmt = select(User).where(
    User.email == "aryan@example.com"
)

user = session.scalar(stmt)

Conceptually this produces SQL like:

SELECT id, name, email
FROM users
WHERE email = 'aryan@example.com';

11. ORM class vs instance

class User(Base):
    ...

User is the ORM class/model.

user = User()

user is an instance of that class.

Therefore:

User
 ↓
class/model

user
 ↓
particular ORM object/instance

There is an important distinction between class-level column expressions and instance-level attribute values.

For example:

User.email == "aryan@example.com"

uses User.email as a SQLAlchemy column expression to construct a query condition.

While:

user.email

reads the actual email value from a particular ORM instance.

Class builds SQL. Instance holds a value. User.email is a column expression. user.email is the email on one object.

12. Console representations

If you print a default Python ORM object without defining a custom __repr__, you may see:

<app.modules.tasks.model.TaskModel object at 0x10e8bd160>

This is a Python object representation, not the JSON representation returned by FastAPI.

If you want to inspect the actual fields in a console, you can explicitly print them or serialize the ORM object using your Pydantic response model.

The SQLAlchemy Engine is the central database connectivity object.

It coordinates:

  • connection pooling
  • database driver usage
  • execution of SQL/database operations
Not PostgreSQL. The Engine is not the PostgreSQL database itself.

An Engine is not one single database connection.

The Engine manages access to connections, normally through a connection pool.

A Connection is an individual database connection obtained from the Engine.

7. echo=True

For development/debugging, you can use:

engine = create_engine(
    DATABASE_URL,
    echo=True
)

This causes SQLAlchemy to log SQL statements and related engine activity.

For example, you may see output resembling:

SELECT users.id, users.name, users.email
FROM users
WHERE users.id = %(id_1)s

The exact output depends on the SQLAlchemy version, driver, logging configuration, and statement.

Development tool. echo=True is useful while debugging, but should be configured thoughtfully in production because SQL/log output can be noisy and potentially expose sensitive information.

6. Declarative Models 10 / 10

A model is a Python class that describes a table. Creating an instance of that class creates a Python object — the row appears only after the Session persists it.

1. What is a declarative model?

A declarative model is a Python class used to describe a database table and map database rows to Python objects.

Example:

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

class Base(DeclarativeBase):
    pass


class TaskModel(Base):
    __tablename__ = "user_tasks"

    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    description: Mapped[str]
    is_completed: Mapped[bool] = mapped_column(default=False)
    user_id: Mapped[int]

2. Base

Base is the declarative base class used by the ORM models.

Models inherit from it:

class TaskModel(Base):
    ...

3. __tablename__

__tablename__ = "user_tasks"

This specifies the database table name associated with the ORM model.

4. Mapped

id: Mapped[int]

Mapped[int] communicates Python-side type information and indicates that the attribute is part of SQLAlchemy's ORM mapping.

5. mapped_column

id: Mapped[int] = mapped_column(
    primary_key=True
)

mapped_column() provides database-column configuration.

6. Class vs instance

TaskModel

is the ORM class.

task = TaskModel()

creates an instance of that class.

Then:

task.title

represents the value stored in that particular Python ORM object's title attribute.

Whereas:

TaskModel.title

is used in SQLAlchemy expressions to refer to the mapped column expression.

7. Querying through model columns

select(TaskModel).where(
    TaskModel.user_id == user.id
)

Here TaskModel.user_id is not the user ID of one particular Python object. It is the SQLAlchemy mapped column expression.

Conceptually this becomes:

SELECT ...
FROM user_tasks
WHERE user_id = 2;

8. Creating an ORM object does not create a database row

task = TaskModel(
    title="Learn SQLAlchemy",
    description="Learn ORM",
    user_id=2
)

This creates a Python object.

At this point PostgreSQL has not necessarily received an INSERT.

Later:

db.add(task)
db.commit()

causes SQLAlchemy to persist the object as part of the transaction.

Python object first. TaskModel(...) does not INSERT. db.add() and db.commit() are what persist it.

3. Mapped[int]

id: Mapped[int]

The int describes the Python-side type of the mapped attribute.

4. mapped_column()

id: Mapped[int] = mapped_column(
    primary_key=True
)

This describes the database column and its configuration.

5. Explicit vs inferred database type

You can write:

id: Mapped[int] = mapped_column(
    primary_key=True
)

or explicitly specify a SQLAlchemy type:

id: Mapped[int] = mapped_column(
    Integer,
    primary_key=True
)

SQLAlchemy can infer many database types from the Python annotation, but explicit types are useful when you need more precise database behavior.

6. Nullable values

title: Mapped[str | None]

This means the Python value can be either a string or None.

At the database level, None corresponds conceptually to SQL NULL.

Python        Database
None     →    NULL

7. nullable=False

description: Mapped[str] = mapped_column(
    String,
    nullable=False
)

nullable=False means the database column cannot contain NULL.

description = "Learn SQLAlchemy"  ✓
description = NULL                ✗

8. Primary key

id: Mapped[int] = mapped_column(
    primary_key=True
)

primary_key=True is database column/constraint configuration, not a Python type.

A primary key identifies a row.

9. unique=True

email: Mapped[str] = mapped_column(
    String,
    nullable=False,
    unique=True
)

This tells the database that duplicate values should not be allowed for the column under the generated uniqueness constraint.

Application-level checks are still useful, but database constraints provide the final integrity guarantee.

10. default

is_completed: Mapped[bool] = mapped_column(
    Boolean,
    default=False
)
Python-side default. default=False is a SQLAlchemy-side default. It should not automatically be interpreted as a PostgreSQL DEFAULT FALSE clause.

11. server_default

A server-side default is configured differently and is handled by the database.

Conceptually:

default
  ↓
SQLAlchemy/application-side behavior

server_default
  ↓
database/server-side behavior

SQLAlchemy provides different string-related database types.

13. Real-world type decision: phone number

mobile_number: Mapped[str]

A phone number is generally better represented as a string because it is an identifier rather than a quantity.

It may contain:

country codes
-
formatting

You normally do not perform mathematical operations on phone numbers.

14. ForeignKey

user_id: Mapped[int] = mapped_column(
    ForeignKey("users.id", ondelete="CASCADE")
)

ForeignKey is a database constraint rather than a data type.

It says that the value in user_id references users.id.

ondelete="CASCADE" defines deletion behavior at the database relationship level and will be studied in depth with foreign keys and relationships.

An ORM object moves through states based on its relationship with a Session and the database. Those states are separate from whether the current transaction has been committed, and separate from whether the Python object still exists in memory.

1. ORM object lifecycle

   └──→ Detached

Persistent describes the ORM object's relationship with the Session/database identity. Committed describes the state of the current transaction.

Object → Persistent
Transaction → still open
Two different facts. Persistent is an ORM state. Committed describes the transaction. An object can be persistent while the transaction is still open.

6. In-Memory Assignment vs Persistence

7. Can relationship() Work Without back_populates?

8. Can relationship() Work Without a ForeignKey?

Yes, if you explicitly tell SQLAlchemy how the tables are related. Without foreign-key metadata, SQLAlchemy generally cannot infer the join condition automatically.

Example: the user_id column exists, but is just an integer column without a database ForeignKey constraint.

from sqlalchemy import Integer
from sqlalchemy.orm import Mapped, mapped_column, relationship, foreign

class UserModel(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    tasks: Mapped[list["TaskModel"]] = relationship(
        primaryjoin="UserModel.id == foreign(TaskModel.user_id)",
        back_populates="user",
    )


class TaskModel(Base):
    __tablename__ = "user_tasks"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(Integer)

    user: Mapped["UserModel"] = relationship(
        primaryjoin="foreign(TaskModel.user_id) == UserModel.id",
        back_populates="tasks",
    )

primaryjoin explicitly describes the join condition. foreign() marks the foreign-key side for ORM relationship purposes. This does not create a database FK constraint or protect against invalid IDs.

18. One-to-Many Relationships 9 / 10

1. The Core Concept

A one-to-many relationship means one record in a parent table can be associated with zero, one, or many records in a child table.

  • A user is allowed to have no tasks.

    user: Mapped["UserModel"] = relationship(
        back_populates="tasks"
    )

DeclarationMeaning
user_id: Mapped[int]The mapped attribute is an integer.
mapped_column(...)Declares a mapped database column.
ForeignKey("users.id")Declares a database-level reference to users.id.

back_populatesConnects opposite relationship attributes.
Type difference: UserModel.tasks is a collection, so it uses Mapped[list["TaskModel"]]. TaskModel.user refers to one user, so it uses Mapped["UserModel"].

4. Creating and Saving Related Objects

Approach A: Create the parent and append children

user = UserModel(username="Aryan")

task1 = TaskModel(title="Learn SQLAlchemy")
task2 = TaskModel(title="Learn FastAPI")
task3 = TaskModel(title="Learn PostgreSQL")

user.tasks.append(task1)
user.tasks.append(task2)
user.tasks.append(task3)

db.add(user)
db.commit()

Appending tasks to user.tasks associates them with that user through the ORM relationship. With the usual relationship cascade configuration, adding the parent to the session also brings related new tasks into the unit of work. SQLAlchemy coordinates insert order and foreign-key values during persistence.

Approach B: Assign the relationship from the child

user = db.get(UserModel, 1)

task = TaskModel(
    title="Learn Docker",
    user=user,
)

db.add(task)
db.commit()

task.user = user associates the task with that specific user object.

Approach C: Assign the foreign-key ID directly

task = TaskModel(
    title="Learn Docker",
    user_id=1,
)

db.add(task)
db.commit()

This sets the foreign-key attribute directly. The database constraint checks that the referenced user exists when the insert is checked by the database.

Important: SQLAlchemy does not automatically select a “current user.” Your code must associate the task with a specific user or provide the intended user_id.

5. Reading Related Objects

Get a user and read their tasks

user = db.get(UserModel, 1)

if user is not None:
    for task in user.tasks:
        print(task.title)

Get a task and read its user

task = db.get(TaskModel, 101)

if task is not None:
    print(task.user.username)

Depending on the loading strategy and whether related data is already available, accessing user.tasks or task.user can issue additional SQL. Relationship loading strategies and the N+1 query problem are covered in later topics.

6. Foreign Key vs. ORM Relationship

ConceptExampleResponsibility
Foreign-key columntask.user_idStores the user's ID in the database row.
ORM relationshiptask.userProvides access to the associated UserModel object.
Collection relationshipuser.tasksProvides access to associated task objects.
task.user = user       # Associate through an ORM object
task.user_id = user.id # Set the foreign-key value directly

Both can represent the same database association when used correctly, but they operate through different mapped attributes. Relationship assignment is especially useful when the parent is new and its generated ID is not available yet.

7. Common Mistakes and Nuances

  • Putting the foreign key on the wrong side: in this one-to-many schema, each task row stores user_id.
  • Confusing relationship and column: relationship() does not create the user_id column.
  • Assuming every user needs a task: an empty user.tasks collection is valid.
  • Forgetting nullability: nullable=False forbids a missing ID; the foreign-key constraint ensures the ID refers to an existing user.
  • Assuming assignment equals persistence: changes are persisted through the session's flush/transaction workflow.
  • Assuming relationship access never runs SQL: behavior depends on loading strategy and session state.
  • Assuming model edits update an existing schema: use migrations, typically Alembic, to manage schema changes.

9. Quick Recap

  • One user can be related to many tasks.
  • The child table stores the foreign key: user_tasks.user_id.
  • user.tasks is a collection; task.user is one user object.
  • ForeignKey defines database referential integrity; relationship() configures ORM navigation.
  • Relationship assignment and session persistence are connected, but they are not the same operation.
One-sentence mental model: The database stores the parent ID on each child row, while SQLAlchemy's relationships let you work with those associations as Python objects.
